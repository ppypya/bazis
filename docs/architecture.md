# Архитектура кода

## Направление зависимостей

```text
presentation ──────→ application ──────→ domain
infrastructures ───→ application / domain
config/ioc ────────→ сборка конкретных компонентов
```

Стрелки обозначают разрешённое направление импортов. При выполнении
сценарий может вызывать инфраструктурный адаптер через интерфейс,
объявленный в `application/interfaces`.

## Domain

Домен содержит бизнес-модель и её инварианты:

- `entities` — сущности с идентичностью и поведением, например платёж.
- `value_objects` — значения, например сумма с валютой.
- `services` — доменные операции, которые не принадлежат одной сущности.
- `exceptions.py` — ошибки нарушения бизнес-правил.

Домен не импортирует остальные слои, ORM, HTTP-фреймворки или брокер.
Допустимость смены статуса платежа проверяется здесь.

## Application

Прикладной слой описывает сценарии и координирует работу домена:

- `use_cases` — `CreatePayment`, `GetPayment`, `ProcessPayment` и `PublishOutbox`.
  `ProcessPayment` последовательно выполняет оплату и отправку webhook.
- `dtos` — входные и выходные данные сценариев, независимые от транспорта.
- `interfaces` — контракты репозиториев, Unit of Work, платёжного шлюза,
  отправителя webhook и публикации сообщений.
- `exceptions.py` — ошибки сценариев, например конфликт ключа идемпотентности.

Сценарии зависят от интерфейсов, а не от конкретных адаптеров.
`CreatePayment` проверяет допустимость webhook через `WebhookURLValidator`
до открытия транзакции. Поэтому правило действует при вызове из API, CLI
или другого обработчика. Контроллер преобразует `WebhookRejected` в HTTP 422.
HTTP-коды, RabbitMQ ACK и SQLAlchemy Session в этот слой не передаются.
Для интерфейсов предполагается использование `typing.Protocol`,
для DTO — обычных Python-классов или `dataclass`.

## Presentation

Входные адаптеры преобразуют внешний вызов во входные данные сценария:

- `api` — HTTP-контроллеры, Pydantic-схемы и зависимости FastAPI.
- `cli` — команды запуска и административные команды.
- `consumers` — обработчики сообщений RabbitMQ.
- `jobs` — точки входа для периодических задач.

Контроллеры и обработчики вызывают use case, затем преобразуют результат
или ошибку в ответ соответствующего транспорта. Они не работают напрямую
с SQLAlchemy-моделями и не содержат бизнес-правил.

## Infrastructures

Внешние адаптеры реализуют контракты прикладного слоя:

- `db` — SQLAlchemy-модели, репозитории и Unit of Work.
- `broker` — адаптер публикации сообщений в RabbitMQ.
- `mappers` — преобразования доменных сущностей и инфраструктурных моделей.
- `external_apis` — эмулятор платёжного шлюза с задержкой 2–5 секунд.
  Он реализует интерфейс шлюза и может быть заменён HTTP-адаптером.
- `webhooks` — HTTP-отправитель уведомлений, реализация политики URL и безопасный транспорт.
  При каждой отправке транспорт проверяет все DNS-адреса и подключается
  к проверенному IP с исходными Host и TLS-именем. Это защищает от смены
  DNS между созданием платежа и отправкой. Redirects отключены.

ORM-модели отделены от доменных сущностей. Реализации адаптеров получают
настройки и зависимости при создании.

## Config и сборка приложения

Конфигурационные модули описывают параметры приложения, БД, брокера,
внешних API и CORS. `settings.py` объединяет настройки.

`config/ioc` выполняет роль Composition Root: создаёт конкретные адаптеры
и передаёт их сценариям. Отдельный пакет `bootstrap` не требуется.
Точки запуска API и воркеров используют эту сборку; работающие контроллеры
и сценарии получают готовые зависимости.

Создание и закрытие подключений выполняется явно в жизненном цикле
процесса. Импорт модулей не должен открывать подключения или запускать
фоновые задачи.

## Транзакции и асинхронная обработка

Границами транзакций управляет use case через Unit of Work.
Репозитории самостоятельно не вызывают `commit`.

Создание платежа и запись задания в outbox выполняются в одной транзакции.
Результат платежа фиксируется до отправки webhook. При ошибке счётчик попыток
и задание retry/DLQ записываются в одной транзакции. Публикация outbox
выполняется отдельным сценарием через интерфейс брокера.

Вызов платёжного шлюза и отправка webhook происходят вне транзакций БД.
Для обращения к шлюзу обработка разделяется на фиксацию начала попытки,
сетевой вызов и сохранение результата. Эмулятор возвращает стабильный результат
по ID платежа при повторном вызове. Для реального шлюза понадобятся
идемпотентность и сверка неопределённого результата.

Состояние платежа и состояние доставки уведомления учитываются отдельно.
Повтор webhook не запускает оплату. Обработчики должны учитывать повторную
доставку сообщений и сохранять результат либо надёжное задание продолжения
до подтверждения сообщения.

## Проверка реализации

`tests/unit` предназначен для правил домена и прикладных сценариев
с подставными реализациями интерфейсов.

`tests/integration` предназначен для проверки адаптеров, транзакций,
HTTP-контрактов и взаимодействия с PostgreSQL, RabbitMQ и эмулятором шлюза.

`migrations/versions/0001_payments_outbox.py` создаёт две прикладные таблицы.
Дополнительно Alembic использует свою таблицу версий.

## Запуск и DI

`config/api.py` создаёт FastAPI-приложение; `config/worker.py` — FastStream.
`config/ioc/container.py` собирает адаптеры и сценарии. FastAPI `Depends`
используется только во входном HTTP-адаптере. CLI запускает сборку приложения,
поэтому его точка запуска импортирует `config.worker`.

Consumer подписан только на `payments.new`. Отдельная asyncio-задача
публикует outbox. Retry-очереди не имеют собственных обработчиков:
TTL и DLX возвращают сообщения в основную очередь.

Каждый Unit of Work создаёт отдельную AsyncSession. Engine и HTTP-клиент
переиспользуются в пределах процесса и закрываются при завершении.
